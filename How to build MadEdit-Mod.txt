Requirements
============
* Autotools: autoconf 2.69, automake 1.16, libtool, gettext-devel, m4
* A C/C++ toolchain (GCC or Clang) and make
* wxWidgets 3.3 or later, built with UNICODE support
  (the source uses wxWidgets 3.3 APIs such as wxList::compatibility_iterator
   and wxAuiNotebookPageArray)
* Boost headers (Boost.Xpressive and Boost.Python headers are used;
  no Boost binary library is required, the Boost.Python implementation
  is bundled in the python/ directory)

The wxWidgets and pkg-config macros used by autoconf are bundled in the
m4/ directory (m4/wxwin.m4 and m4/pkg.m4), so a system-wide installation
of wxwin.m4 is no longer required.

Building on Linux
=================
* Install the development packages, for example on Debian/Ubuntu:

    apt install build-essential autoconf automake libtool gettext \
        libgtk-3-dev libwxgtk3.2-dev libboost-dev

* Bootstrap and build:

    sh ./autogen.sh
    ./configure
    make
    make install

  wxWidgets is detected with wx-config.  The GTK+/glib flags are only
  added when the wxWidgets build actually uses the GTK port, so a
  wxWidgets built against GTK2/GTK3 is used as is.

Building on Windows (MSYS2 / MinGW-w64, x86_64)
==============================================
The most convenient way is the autotools build under MSYS2, because it
is the same build system that is used on Linux and macOS.

* Install MSYS2 and the required packages from the "MSYS2 UCRT64" shell:

    pacman -S mingw-w64-ucrt-x86_64-wxwidgets3.3-msw \
               mingw-w64-ucrt-x86_64-boost \
               autoconf2.69 automake1.16 gettext-devel libtool

* Build:

    sh msw/build-msys2.sh

  The script regenerates configure/Makefile.in when needed, runs
  ./configure and make, and finally assembles dist/.  The result is
  ./madedit.exe and a self-contained ./dist/ folder that can be copied
  to any Windows machine.

  Add --enable-debug to get a build with debug info and assertions
  instead of the default release build (-O2 -DNDEBUG).

  madedit.exe needs the wxWidgets DLLs at runtime; they are copied
  into dist/ next to the executable, so no PATH setup is needed there.
  When running ./madedit.exe straight from the build tree, /ucrt64/bin
  has to be in PATH (it is by default inside the UCRT64 shell).

  The dist/ layout follows what the Windows build looks for relative to
  the executable:

    dist/madedit.exe
    dist/syntax/        syntax highlighting definitions
    dist/scripts/       MadPython macro scripts
    dist/Dictionaries/  hunspell dictionaries
    dist/locale/        translations (<lang>/LC_MESSAGES/madedit-mod.mo)
    dist/*.dll          wxWidgets and MinGW runtime DLLs

  Notes about the MinGW build:
  - MadEdit is a single instance application.  If an instance is already
    running, a newly started copy only forwards its command line to the
    running one and exits, so a fresh build may appear to do nothing
    (and an old instance may keep showing an outdated warning dialog).
    Kill the running instance before testing a new build.
  - The minipython sources are compiled as C17 (-std=gnu17).  GCC 14 and
    later default to C23, where bool/false/true became keywords and
    K&R style function definitions were removed, which breaks the
    Python 2.7 sources.
  - Py_NO_ENABLE_SHARED is defined, otherwise pyconfig_win.h declares
    the Python API with __declspec(dllimport) even though minipython is
    linked statically.  The same applies to BOOST_PYTHON_STATIC_LIB and
    HUNSPELL_STATIC.
  - wxWidgets resources are compiled into the executable with windres:
    wx_manifest_res.rc pulls in the Windows manifest (Common Controls v6
    and per-monitor-v2 DPI awareness) and src/MadEditApp.rc provides the
    application icon (images/Mad2.ico), the version information and the
    wxWidgets standard icons and cursors.  Without them wxWidgets shows a
    "wxWidgets Warning" dialog on startup and the application has no
    icon.
  - The icon resources and the manifest have to be compiled into two
    separate resource objects: when ld merges two .rsrc sections it does
    not renumber the RT_ICON ids, so both objects would start at id 1
    and the icons would end up pointing at each other's images.
  - The executable uses the console subsystem, like the Visual Studio
    build, so a console window accompanies the editor window.

Building on Windows (MSVC)
==========================
The Visual Studio projects are in msw/vc18 (VS 2026, toolset v145) and
msw/vc17 (VS 2022, toolset v143).  Open MadEdit.sln and build the
Release|x64 or Debug|x64 configuration.  They expect:
  * WXWIN  - an unpacked wxWidgets MSW build (include\ and lib\vc_x64_lib)
  * BOOST_ROOT - the Boost headers
The project builds minipython, the bundled Boost.Python and hunspell
itself.

The vc18 projects compile as C++17 (the bundled astyle 3.5.1 requires
it).  Like vc17 they link the static CRT (/MT, /MTd), so wxWidgets has
to be built as static libraries with the static CRT as well:

* Download and unpack the wxWidgets 3.3 sources, e.g. to
  D:\Devel\wxWidgets-3.3.2, and Boost, e.g. to D:\Devel\boost_1_91_0
  (only the headers are used, Boost does not have to be built).

* Create build\msw\wx_local.props in the wxWidgets tree:

    <?xml version="1.0" encoding="utf-8"?>
    <Project ToolsVersion="4.0"
             xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
      <PropertyGroup Label="UserMacros">
        <wxRuntimeLibs>static</wxRuntimeLibs>
        <wxReleaseRuntimeLibrary>MultiThreaded</wxReleaseRuntimeLibrary>
        <wxDebugRuntimeLibrary>MultiThreadedDebug</wxDebugRuntimeLibrary>
      </PropertyGroup>
    </Project>

* Build wxWidgets from a "Developer PowerShell for VS 2026":

    msbuild build\msw\wx_vc17.sln /m /p:Configuration=Release /p:Platform=x64 /p:PlatformToolset=v145
    msbuild build\msw\wx_vc17.sln /m /p:Configuration=Debug /p:Platform=x64 /p:PlatformToolset=v145

  The libraries end up in lib\vc_x64_lib.

* Set the environment variables (restart Visual Studio afterwards) and
  build MadEdit:

    setx WXWIN D:\Devel\wxWidgets-3.3.2
    setx BOOST_ROOT D:\Devel\boost_1_91_0
    msbuild msw\vc18\MadEdit.sln /m /p:Configuration=Release /p:Platform=x64

  The result is msw\vc18\x64\Release\MadEdit.exe.  It reads its
  configuration (MadEdit.cfg) and the syntax/, scripts/, Dictionaries/
  and locale/ folders from the directory of the executable.

Building on macOS
=================
The easiest way is the helper script, which builds the program and assembles
a double clickable MadEdit.app:

    sh macos/build-macos.sh

It installs nothing by itself; it expects the dependencies below to be
present, and it puts the build tree in /opt/local/madedit-build (or in
~/local/madedit-build when /opt/local is not writable).  Options:

    sh macos/build-macos.sh --build-dir=PATH   use another build directory
    sh macos/build-macos.sh --prefix=PATH      installation prefix
    sh macos/build-macos.sh --relocatable      bundle the dylibs into the .app
    sh macos/build-macos.sh --debug            build with debug info

The plain autotools build works as well:

    sh ./autogen.sh
    ./configure
    make

Requirements:
  * wxWidgets 3.3 or later, built for macOS (the Cocoa port)
  * Boost headers (Boost.Xpressive and Boost.Python headers)
  * Xcode command line tools
  * GNU gettext, for the translations

With Homebrew:

    brew install wxwidgets boost gettext

The .app bundle
---------------
macos/build-macos.sh produces MadEdit.app with this layout:

    MadEdit.app/Contents/MacOS/MadEdit              the executable
    MadEdit.app/Contents/Resources/syntax/          syntax highlighting
    MadEdit.app/Contents/Resources/scripts/         MadPython macros
    MadEdit.app/Contents/Resources/Dictionaries/    hunspell dictionaries
    MadEdit.app/Contents/Resources/locale/          translations
    MadEdit.app/Contents/Resources/MadEdit.icns     the icon
    MadEdit.app/Contents/Info.plist

The executable looks for its data files in the directory it lives in, so on
macOS the program redirects that lookup to Contents/Resources when it detects
that it is running from a bundle.  Drag the whole MadEdit.app into the
Applications folder and it is ready to use.

By default the executable links against the wxWidgets and gettext libraries
in Homebrew, so the .app only runs on a machine that has the same libraries
installed.  Use --relocatable to copy the libraries into
MadEdit.app/Contents/Frameworks and rewrite the load paths, which makes the
bundle self contained.

Notes:
  * macOS uses the wxWidgets Cocoa port, so neither GTK+ nor X11 is
    required; configure only adds the GTK+/glib and -lX11 flags when the
    wxWidgets build actually uses the GTK port.
  * The default file system of macOS is case insensitive.  The VERSION
    file at the top of the source tree was therefore renamed to
    VERSION.txt: on a case insensitive file system "VERSION" shadows the
    C++20 standard header <version>, which breaks every translation unit
    that includes <boost/config.hpp>.
  * minipython/Modules/getpath.c is used on macOS; it contains the
    mach-o/dyld based path detection.
  * The bundled astyle 3.5.1 requires C++17, so the C++ compiler must be
    invoked with -std=c++17 or newer (clang defaults to gnu++17 since
    Xcode 15).
  * minipython ships its own pyconfig.h.  It selects a header by platform
    and macOS is handled by minipython/Include/pyconfig-macos.h, because
    macOS does not define __unix__.
  * The single instance mechanism uses a unix socket in /tmp.  The name
    contains the user name so that two users on the same machine do not
    remove each other's socket.  When the socket cannot be created the
    program falls back to running as a second instance instead of exiting
    silently.
  * The executable is ad-hoc signed by the build script.  Apple Silicon
    refuses to start unsigned executables.

wxWidgets 3.3 notes
===================
wxWidgets 3.3 changed wxAuiNotebook::AddPage(): the page has to be created
with the notebook as its parent, otherwise AddPage() fails and no page is
ever shown.  MadEdit creates its editor pages with the frame as the parent
(wx 2.8 reparented them automatically), so the parent was changed to the
notebook in src/MadEditFrame.cpp.
